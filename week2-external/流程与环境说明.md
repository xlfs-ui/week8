# week2-external：对话应用流程、环境与 API 密钥说明

本文用文字描述「流程图」、环境配置方式，以及前后端与 `api_key` 相关的调用链（理论说明）。

---

## 一、文字流程图（端到端）

```
[用户浏览器]
    |
    | ① 打开首页
    v
GET /  -------------------------->  [FastAPI：返回 frontend/index.html 与静态资源]
    |
    | ② 用户输入消息，点击发送
    v
POST /api/chat  (JSON: { messages: [...] })
    |
    | ③ FastAPI 校验请求体（Pydantic）
    v
[FastAPI 路由 chat()]
    |
    | ④ 调用 deepseek_chat.completion()
    v
[服务端：读取环境变量 DEEPSEEK_API_KEY]
    |
    | ⑤ 使用 OpenAI 兼容客户端，HTTPS 请求
    v
POST https://api.deepseek.com/.../chat/completions
    (Authorization: Bearer <API_KEY>，仅存在于服务端发出的 HTTP 头中)
    |
    | ⑥ DeepSeek 返回模型输出
    v
[FastAPI 封装为 JSON：{ "reply": "...", "model": "..." }]
    |
    | ⑦ HTTP 200 + JSON 响应体
    v
[浏览器 fetch 解析 JSON，把 reply 显示在对话区]
```

**要点摘要**

1. 首页与静态文件只经过本机 FastAPI，不经过 DeepSeek。
2. 对话内容只以 JSON 形式在「浏览器 ? 本机 FastAPI」之间传输。
3. 与 DeepSeek 的密钥交互只发生在「FastAPI 进程 ? DeepSeek 云端」之间。

## 二、环境配置

### 2.1 Python 依赖

在 `week2-external` 目录下安装 `requirements.txt` 中的包（与课程根目录 Poetry 二选一即可，勿混用两套环境时记清当前 `python` 指向谁）：

- `fastapi`、`uvicorn`：Web 框架与 ASGI 服务器  
- `pydantic`：请求/响应模型校验  
- `python-dotenv`：从 `.env` 加载环境变量  
- `openai`：官方提供的 **OpenAI 兼容 HTTP 客户端**，用于调用 DeepSeek 的兼容接口  

### 2.2 环境变量文件放哪、写什么

**文件路径（重要）**：请把 `.env` 建在 **`week2-external` 目录下**，即与 `app/`、`frontend/` 同级：

```text
modern-software-dev-assignments/     ← 整个作业仓库根目录（不是默认读这里）
  week2-external/
    .env          ← API 密钥写在这个文件里
    app/
      main.py     ← 在这里调用 load_dotenv
    frontend/
```

**不是**「只要在任意根目录建 `.env` 就会自动生效」。本项目**只**会在启动时读取**固定相对路径**的那一个文件，由代码写死逻辑推导出来。

### 2.3 为什么在这里建 `.env`、写上 `DEEPSEEK_API_KEY` 就行？

1. **代码里显式指定了要读哪个文件**  
   在 `app/main.py` 中有：

   - `PACKAGE_ROOT = Path(__file__).resolve().parent.parent`  
     表示「`main.py` 所在目录 `app/` 再向上一级」，也就是 **`week2-external`** 目录本身。  
   - `load_dotenv(PACKAGE_ROOT / ".env")`  
     表示：把 **`week2-external/.env`** 这个路径上的文件读进来。

   因此：**只要 `.env` 放在 `week2-external` 下且文件名是 `.env`**，就和代码里的路径一致；与你在终端里 `cd` 到仓库最外层还是 `cd` 到 `week2-external` **无关**（路径是根据 `main.py` 磁盘位置算的，不依赖当前工作目录去猜 `.env`）。

2. **`python-dotenv` 在做什么**  
   `load_dotenv(...)` 会解析 `.env` 里的多行文本（形如 `KEY=value`），把每一项**合并进当前 Python 进程的环境变量**（`os.environ`）。  
   **默认行为**：若操作系统里**已经**存在同名环境变量（例如在终端里事先 `export` / `set` 过），`python-dotenv` **不会覆盖**已有值，仍以系统里的为准。本地开发若发现改了 `.env` 却不生效，可检查是否曾在 shell 里导出过旧的 `DEEPSEEK_API_KEY`。

3. **业务代码怎么拿到「API key」**  
   `app/services/deepseek_chat.py` 里使用 `os.getenv("DEEPSEEK_API_KEY", "")`。  
   进程启动后，只要前面 `load_dotenv` 已成功把 `DEEPSEEK_API_KEY` 写进 `os.environ`，这里就能读到——**不需要**你在代码里手写密钥字符串，也**不需要**前端传 key。

4. **若把 `.env` 只建在「整个 Git 仓库根目录」**（例如 `modern-software-dev-assignments/.env`）  
   按当前代码，**不会**自动加载那个文件，除非：  
   - 你改 `load_dotenv` 的路径指向仓库根，或  
   - 你在操作系统 / 终端里已经 `export` / `set` 了 `DEEPSEEK_API_KEY`（不依赖 `.env` 文件也能工作）。

**`.env` 示例**（每行一个键值，不要加引号也可以，值里若有空格再按 dotenv 规则处理）：

```env
DEEPSEEK_API_KEY=sk-你的密钥
# 可选
# DEEPSEEK_MODEL=deepseek-v4-flash
# DEEPSEEK_BASE_URL=https://api.deepseek.com
```

| 变量名 | 是否必填 | 含义 |
|--------|----------|------|
| `DEEPSEEK_API_KEY` | 必填（对话功能） | DeepSeek 控制台发放的密钥，仅服务端使用 |
| `DEEPSEEK_MODEL` | 可选 | 模型 ID，默认可为 `deepseek-v4-flash` 等官方文档中的名称 |
| `DEEPSEEK_BASE_URL` | 可选 | 默认可为 `https://api.deepseek.com` |

**安全习惯**：将 `.env` 加入 `.gitignore`，不要把真实密钥提交到 Git。

### 2.4 启动命令

在 **`week2-external`** 作为当前工作目录时执行（保证 `app` 包可被导入）：

```bash
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

浏览器访问：`http://127.0.0.1:8000/`。

## 三、前后端响应与 `api_key` 的流程（理论）

### 3.1 前端（浏览器）不持有、不传输 `api_key`

- 前端脚本（`frontend/app.js`）只调用**同源**接口：`fetch("/api/chat", { method: "POST", body: JSON.stringify({ messages }) })`。
- 请求体里只有对话角色与文本（`messages`），**没有**也不应出现任何 API 密钥字段。
- 因此：即使用户打开开发者工具查看网络面板，也只能看到发往本机的 JSON，**看不到** DeepSeek 的 `api_key`。

### 3.2 后端在进程内读取密钥并代表用户调用云端

1. 服务**导入 `app.main` 时**会执行 `load_dotenv(PACKAGE_ROOT / ".env")`，把 **`week2-external/.env`** 里的键值写入**当前 uvicorn 子进程**的 `os.environ`（与第二节对应：不是「任意根目录」，而是代码绑定的那个路径）。
2. `deepseek_chat.get_client()` 从 **`os.getenv("DEEPSEEK_API_KEY")`** 读取字符串，构造 `OpenAI(api_key=..., base_url=...)`。
3. `client.chat.completions.create(...)` 在底层发出 HTTPS 请求时，由客户端库在 HTTP 头中加入 **`Authorization: Bearer <DEEPSEEK_API_KEY>`**（具体格式以库与 DeepSeek 文档为准）。
4. 密钥**从未**作为 JSON 字段返回给浏览器；成功时仅返回业务字段，例如 `reply` 与 `model`。

### 3.3 信任边界小结

| 位置 | 是否接触 `api_key` |
|------|---------------------|
| 用户浏览器 / 前端 JS | 否 |
| 浏览器到 FastAPI 的 HTTP 请求/响应 | 否（仅 messages 与模型回复摘要） |
| FastAPI 进程内存与环境变量 | 是（仅服务端） |
| FastAPI 到 DeepSeek 的 HTTPS 出站请求 | 是（放在服务端发起的鉴权头中） |

**理论结论**：这是一种典型的 **BFF（Backend-for-Frontend）/ 代理式** 用法——浏览器只信任本机（或部署域上的）FastAPI；**高敏感凭证停留在服务端**，由服务端单独与第三方大模型 API 建立信任关系。

## 四、与课程参考目录的对应关系（简述）

- **week2**：同样使用 FastAPI 提供 HTTP 接口与静态页挂载方式，本项目的路由与 `StaticFiles` 思路一致。  
- **mcp-client-python**：同样使用 `OpenAI` 客户端 + `base_url` 指向 DeepSeek；本项目改为纯 HTTP JSON 对话，不经过 MCP 子进程。
